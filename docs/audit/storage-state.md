# storage-state — info findings

All four are RSKIP text problems, not code problems. The unitrie is the one
area where following the spec over rskj would corrupt the trie outright, so
each was checked against `co.rsk.trie.Trie` directly.

## FRCR-377 — embedded-node size bound is 44 bytes, spec says "up to 40 bytes"

**Verdict: spec is stale.** rskj:

```java
private static final int MAX_EMBEDDED_NODE_SIZE_IN_BYTES = 44;   // Trie.java:68
return isTerminal() && getMessageLength() <= MAX_EMBEDDED_NODE_SIZE_IN_BYTES;
```

rustock: `const MAX_EMBEDDED_NODE_SIZE: usize = 44;` (`crates/trie/src/node.rs:17`).

Identical. Acting on the RSKIP's "40" would change which nodes are embedded,
which changes node messages, which changes hashes — a fork of the state root
from the first affected node. This is the clearest case in the whole audit of a
recommendation that must **not** be followed.

## FRCR-375 — flags-byte present/embedded bit descriptions mislabelled

**Verdict: spec is stale.** A documentation defect in RSKIP-107. rustock's
parser is checked byte-for-byte against vectors generated by running rskj's own
compiled classes (`crates/trie/tests/rskj_vectors.rs`), which is a stronger
statement about the encoding than the prose is.

## FRCR-373 — RSKIP-16 key layout superseded by RSKIP-108

**Verdict: spec is stale.** The audit says so itself. rustock implements
RSKIP-108, which is what rskj does.

## FRCR-379 — hash-prefix notation `[0:9]` under-specifies the 80-bit prefix

**Verdict: spec is stale.** Notation ambiguity in the RSKIP; the implementation
follows rskj's 10-byte prefix.
